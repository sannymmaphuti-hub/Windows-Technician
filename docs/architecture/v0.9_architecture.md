# Windows Technician v0.9 Architecture

## 1. Purpose

Define the canonical architecture of Windows Technician v0.9.

This document describes the production architecture, domain boundaries, intelligence model, remediation safety model, fleet capabilities, user interface boundary, packaging architecture, security model, documentation structure, and production-readiness principles.

The architecture exists to ensure that new capabilities extend the existing system rather than introducing parallel lifecycles, duplicate domain concepts, or unsafe execution paths.

---

Windows Technician v0.9 covers:

- application lifecycle
- production services
- configuration

- recovery

- remediation boundaries

- user interface presentation

## 3. Core Architectural Principle

New functionality MUST integrate with existing canonical boundaries.

New functionality MUST NOT create:

- parallel diagnostic lifecycles
- parallel remediation lifecycles
- duplicate case models
- duplicate workflow models
- independent recovery lifecycles
- UI-owned diagnostic reasoning
- UI-owned remediation decisions
- blind automatic retries
- bypasses around authorization
- bypasses around verification

The architecture is evolutionary: new capabilities extend established contracts rather than replacing them with competing abstractions.

---

## 4. Canonical Intelligence Chain

The canonical intelligence chain is:

Observation → Signal → Correlation → Finding → Root Cause → Explanation → Recommendation → Diagnostic Case

### Observation

An Observation represents collected evidence about the Windows system.

### Signal

A Signal represents a meaningful condition derived from observations.

### Correlation

Correlation connects related signals and evidence.

### Finding

A Finding represents a diagnostic conclusion supported by evidence.

### Root Cause

Root Cause reasoning identifies candidate causes that explain the observed condition.

### Explanation

Explanation translates diagnostic reasoning into understandable language.

### Recommendation

Recommendation Intelligence determines what should be considered next.

### Diagnostic Case

The DiagnosticCase is the canonical container for the resulting diagnostic story and evidence.

---

## 5. DiagnosticCase

DiagnosticCase is the canonical diagnostic case model.

A diagnostic case provides the central identity for diagnostic reasoning regardless of how the case originated.

Supported origins include:

- LOCAL
- REMOTE
- PROACTIVE

Machine identity and case identity remain distinct.

A machine may have many cases.

A case belongs to a specific diagnostic context and maintains the evidence, findings, correlations, root causes, explanations, and recommendations associated with that context.

DiagnosticCase is therefore the canonical bridge between evidence collection, intelligence, technician workflow, remediation decisions, and verification.

---

## 6. TechnicianWorkflow

TechnicianWorkflow is the canonical workflow boundary for technician problem solving.

The canonical workflow is:

Case → Evidence → Diagnosis → Decision → Authorization → Remediation → Verification → Recovery → Closure

TechnicianWorkflow coordinates the operational progression of a case without replacing the underlying diagnostic intelligence.

Remote and proactive operations MUST use the existing workflow rather than creating independent case lifecycles.

---

## 7. Diagnostic Reasoning Boundary

Diagnostic reasoning remains separate from remediation execution.

The diagnostic system may:

- collect evidence
- construct observations
- identify signals
- correlate evidence
- construct findings
- reason about root causes
- produce explanations
- produce recommendations
- identify potentially eligible remediation actions

Diagnosis MUST NOT silently authorize or execute remediation.

Remediation authorization is deliberately separate from diagnosis.

---

## 8. Canonical Remediation Chain

The canonical remediation chain is:

Eligibility → Decision → Authorization → Execution → Verification

Each boundary has a distinct responsibility.

### Eligibility

Determines whether an action is technically eligible.

### Decision

Determines whether the action should be selected.

### Authorization

Determines whether execution is permitted.

### Execution

Performs the authorized action.

### Verification

Determines whether the expected result was actually achieved.

Diagnosis does not imply authorization.

Authorization does not imply execution.

Execution does not imply verification.

---

## 9. Executed Is Not Verified

An executed remediation action is not automatically considered successful.

The architecture explicitly distinguishes:

Executed ≠ Verified

Verification must independently establish whether the expected system condition was achieved.

A failed or incomplete verification must remain visible to the workflow and must not be converted into an artificial success state.

---

## 10. Recovery Architecture

Recovery is part of the canonical workflow.

Recovery MUST preserve:

- case identity
- workflow identity
- evidence history
- remediation history
- verification history
- lifecycle state
- operational state

Recovery must not become automatic blind retry.

A failed operation MUST NOT simply be executed again without passing through the appropriate decision and authorization boundaries.

Recovery exists to restore controlled operation and preserve diagnostic history, not to conceal failures.

---

## 11. Application Lifecycle

The production application lifecycle is:

CREATED → STARTING → RUNNING → DEGRADED/FAILED → STOPPING → STOPPED

The canonical production runtime is `ApplicationRuntime`.

ApplicationRuntime coordinates:

- application lifecycle
- production services
- configuration
- operational state
- recovery
- logging
- shutdown

Runtime creation does not implicitly start the application.

Startup and failure boundaries remain explicit.

---

## 12. Production Services

The production application service registry contains the canonical services:

- Configuration
- Diagnostics
- Intelligence
- Logging
- UI

ApplicationRuntime owns lifecycle coordination for these services.

Services must respect their architectural responsibilities and must not bypass the production runtime.

---

## 13. Application Bootstrap

ApplicationBootstrap is the production startup boundary and compatibility facade around the canonical runtime.

The bootstrap is responsible for:

- validating startup inputs
- constructing the runtime
- preparing production configuration
- preparing operational state
- preparing recovery context
- starting the runtime
- stopping the runtime
- exposing controlled startup state

Bootstrap failure MUST NOT silently mutate unrelated runtime lifecycle state.

---

## 14. Configuration Architecture

Configuration follows a layered production boundary.

Configuration sources include:

- user configuration
- system configuration
- production environment configuration
- safe application defaults

User configuration overrides system configuration where appropriate.

Configuration is resolved before production services begin normal operation.

The architecture must prevent configuration handling from becoming an uncontrolled source of runtime side effects.

---

## 15. Safe Defaults

Production defaults prioritize safety.

Canonical defaults include:

- automatic diagnostics: enabled
- remediation authorization: disabled
- remote operations: disabled
- telemetry: disabled
- logging: enabled
- UI theme: system

Diagnostics may identify problems without automatically authorizing destructive or consequential actions.

---

## 16. Runtime Paths

Production runtime data is stored beneath:

`%LOCALAPPDATA%\WindowsTechnician\`

The runtime separates:

- application data
- configuration
- logs
- reports

Runtime paths are initialized before operational state and logging are persisted.

---

## 17. Operational State

Operational state persists the application's previous lifecycle context.

The canonical operational state records:

- schema version
- lifecycle state
- clean shutdown state
- recovery state

Operational state is persisted safely and loaded during startup.

Persistent state supports controlled recovery after an interrupted or unclean application session.

---

## 18. Startup Recovery

Startup recovery evaluates the previous operational state before normal production operation.

The recovery boundary produces a startup recovery context containing:

- previous operational state
- whether recovery is required

Recovery information must remain explicit and observable.

The application must not silently interpret every previous failure as permission to retry operations.

---

## 19. Operational Logging

Logging is a production architectural service.

Logging records operational events such as:

- lifecycle transitions
- startup
- shutdown
- failures
- recovery
- configuration events
- runtime events

The canonical application logging boundary is separate from diagnostic intelligence.

Logging must not become a second diagnostic system.

---

## 20. System-Wide Intelligence

System-Wide Intelligence is the v0.9 direction for moving beyond isolated diagnostic modules.

The system should reason across related evidence rather than treating every Windows subsystem as an independent island.

System-wide intelligence connects:

- CPU evidence
- memory evidence
- process evidence
- storage evidence
- service evidence
- startup evidence
- network evidence
- operating-system evidence
- historical evidence
- remediation history
- verification history

The goal is to understand relationships between conditions and produce a coherent diagnostic story.

System-wide intelligence MUST use the canonical intelligence chain rather than introducing a separate reasoning architecture.

---

## 21. Historical Intelligence

Historical intelligence allows Windows Technician to reason about changes over time.

Historical information may include:

- previous observations
- previous findings
- previous cases
- previous remediation actions
- previous verification results
- health baselines
- recurring conditions

Historical evidence must remain distinguishable from current evidence.

Historical information supports reasoning but must not be treated as current evidence without justification.

---

## 22. Remote Operations

Remote operations use the canonical execution chain:

Technician → RemoteSession → RemoteMachine → Diagnostic → Case → Decision → Remediation → Verification

RemoteSession represents the controlled connection context.

RemoteMachine represents the target machine.

Machine identity and case identity remain distinct.

Remote execution MUST NOT bypass:

Eligibility → Decision → Authorization → Execution → Verification

Remote diagnostics must therefore produce normal diagnostic cases rather than creating a separate remote case model.

---

## 23. Proactive Operations

Proactive operations detect conditions before a user explicitly reports a problem.

Proactive cases MUST use the existing DiagnosticCase and TechnicianWorkflow architecture.

Proactive intelligence may generate:

- alerts
- observations
- cases
- recommendations

A proactive alert must not create an independent remediation lifecycle.

The same safety boundaries apply:

Eligibility → Decision → Authorization → Execution → Verification

---

## 24. Fleet and Multi-Machine Architecture

Fleet capabilities extend the single-machine architecture to multiple managed machines.

Fleet architecture must preserve the distinction between:

- fleet identity
- machine identity
- diagnostic case identity
- technician workflow identity
- operation identity

A fleet operation may target multiple machines, but every machine remains independently identifiable.

A fleet action must not erase per-machine evidence or case history.

Fleet intelligence may correlate patterns across machines while preserving machine-specific evidence.

---

## 25. Fleet Intelligence

Fleet intelligence allows Windows Technician to identify patterns across multiple machines.

Examples include:

- recurring failures
- common software conditions
- common configuration problems
- shared environmental conditions
- repeated remediation failures
- recurring health degradation

Cross-machine correlation must not replace individual machine diagnosis.

Fleet-level conclusions must remain traceable to the underlying machine-level evidence.

---

## 26. User Interface Boundary

The UI is a presentation and interaction layer.

The UI may:

- display diagnostic findings
- display explanations
- display recommendations
- display severity
- display progress
- request confirmation
- present remediation actions
- display verification results
- present recovery information
- provide accessibility and keyboard navigation
- adapt layouts responsively

The UI must NOT:

- diagnose
- construct root causes
- invent recommendations
- authorize remediation
- execute remediation
- perform retries
- verify remediation
- create an alternative diagnostic lifecycle

The UI communicates decisions made by canonical domain services.

---

## 27. Packaging Architecture

Windows Technician is packaged as a Windows application using PyInstaller onedir packaging.

The production executable is:

`WindowsTechnician.exe`

The onedir package contains the executable and its `_internal` runtime dependencies.

The package must be validated before distribution.

Packaging is treated as part of the production architecture rather than as an external build-only concern.

---

## 28. Installation Lifecycle

The verified packaging lifecycle is:

Build → Package → Validate → Install → Run → Upgrade → Run → Uninstall

Installation must preserve the distinction between:

- application files
- persistent user data
- configuration
- logs
- reports

Normal uninstall removes application artifacts while preserving appropriate persistent user data.

Upgrade must validate the incoming package before replacing the installed application.

---

## 29. Documentation Architecture

Documentation is divided into canonical domains:

`docs/user/`

`docs/technician/`

`docs/architecture/`

`docs/developer/`

`docs/release/`

User documentation describes end-user behavior.

Technician documentation describes technician workflows.

Architecture documentation defines system boundaries and invariants.

Developer documentation explains implementation and extension.

Release documentation describes packaging and deployment.

Documentation must reflect the actual architecture rather than speculative future architecture.

## 30. Security and Trust

Windows Technician follows a trust-oriented architecture.

Safety boundaries include:

- explicit authorization
- conservative defaults
- controlled remote operations
- disabled telemetry by default
- evidence preservation
- explicit remediation decisions
- verification after execution
- controlled recovery
- operational logging

The system must favor explainability and controlled action over opaque automation.

## 31. Production Readiness

Production readiness includes:

- application lifecycle correctness
- service lifecycle correctness
- configuration correctness
- persistent operational state
- recovery behavior
- operational logging
- packaging validation
- installation validation
- upgrade validation
- uninstall validation
- documentation
- security boundaries
- performance
- stability
- multi-configuration testing
- beta readiness

A feature is not production-ready merely because its implementation tests pass in isolation.

It must also integrate with the canonical runtime and operational architecture.

---

## 32. Architectural Invariants

The following invariants are mandatory:

1. DiagnosticCase remains the canonical diagnostic case model.
2. TechnicianWorkflow remains the canonical technician workflow.
3. Observation → Signal → Correlation → Finding → Root Cause → Explanation → Recommendation remains the canonical intelligence chain.
4. Eligibility → Decision → Authorization → Execution → Verification remains the canonical remediation chain.
5. Diagnosis does not authorize remediation.
6. Execution does not imply verification.
7. Recovery must not become automatic blind retry.
8. Remote operations must use the canonical case and remediation boundaries.
9. Proactive operations must use the canonical case and workflow boundaries.
10. Fleet operations must preserve machine identity and case identity separately.
11. UI presentation must not become a domain reasoning engine.
12. System-Wide Intelligence must extend the canonical intelligence architecture.
13. Operational state must remain separate from diagnostic case state.
14. Logging must remain separate from diagnostic reasoning.
15. Configuration must remain an explicit production boundary.
16. Packaging must preserve the runtime architecture.
17. Persistent user data must remain distinguishable from application binaries.
18. New features must extend existing canonical boundaries rather than create competing architectures.

---

## 33. Architectural Direction

Windows Technician v0.9 is transitioning from a collection of diagnostic capabilities into a coherent Windows intelligence platform.

The architectural direction is:

Single Machine
→ Multi-Machine
→ Fleet Intelligence
→ System-Wide Intelligence
→ Evidence-Based Reasoning
→ Controlled Remediation
→ Verified Outcomes
→ Historical Learning

The long-term objective is not blind automation.

The objective is a system that can understand what Windows is communicating through evidence, explain what that evidence means, identify relationships between conditions, determine what action is appropriate, obtain authorization before consequential action, execute safely, and verify the result.

The architecture must remain understandable, testable, explainable, and safe as intelligence capabilities expand.
