# Windows Technician V1.0 — Beta Acceptance Matrix

## 1. Purpose

This matrix provides a consistent way to record beta evidence and determine
whether release-blocking conditions remain.

A scenario is not considered passed merely because it was attempted. Record
the actual result and supporting evidence.

## 2. Result definitions

- NOT RUN: no test evidence has been recorded.
- PASS: the expected behavior was observed and evidence was retained.
- FAIL: the scenario did not meet its acceptance criterion.
- BLOCKED: the scenario could not be completed; explain why.
- NOT APPLICABLE: the scenario does not apply to this build; justify the
  exclusion.

Do not mark a scenario PASS based only on documentation or an unexecuted test.

## 3. Acceptance matrix

| ID | Area | Acceptance criterion | Required evidence |
|---|---|---|---|
| BETA-01 | Artifact integrity | Executable exists and its SHA-256 matches the expected release manifest | Artifact path, size and hash |
| BETA-02 | Startup | Packaged application starts in the test environment | Startup result and relevant log |
| BETA-03 | Shutdown | Normal application closure is recorded cleanly | Process state and shutdown log |
| BETA-04 | Runtime paths | Application resolves its supported runtime and user-data paths | Test result and resolved paths |
| BETA-05 | Logging | Operational logs are written to the resolved log location | Log path and representative entries |
| BETA-06 | Diagnostics | Findings are supported by available evidence | Test case and observed findings |
| BETA-07 | Incomplete evidence | Missing evidence is not silently treated as a healthy result | Negative-test evidence |
| BETA-08 | Recommendation safety | A recommendation does not independently authorize execution | Relevant test result |
| BETA-09 | Authorization | Unauthorized operations cannot bypass the required boundary | Negative-test evidence |
| BETA-10 | Verification | Execution success is not confused with verified success | Execution and verification results |
| BETA-11 | Recovery | Failure handling preserves history and avoids blind retries | Recovery test evidence |
| BETA-12 | Remote safety | Remote operations preserve target identity and authorization where supported | Integration and negative tests |
| BETA-13 | Fleet safety | Fleet summaries do not grant blanket remediation authorization | Integration and negative tests |
| BETA-14 | UI | Core screens remain usable at representative sizes and scaling settings | Recorded manual test results |
| BETA-15 | Accessibility | Supported keyboard navigation and focus behavior are usable | Manual test results |
| BETA-16 | Compatibility | Each claimed supported Windows environment has recorded validation | Environment matrix |
| BETA-17 | Documentation | Required guides and local references are present and valid | Documentation validation output |
| BETA-18 | Security and privacy | Shared diagnostic artifacts are reviewed for sensitive information | Review record |
| BETA-19 | Release limitations | Known limitations, including signature status, are disclosed accurately | Release notes or acceptance record |

## 4. Environment record

For each tested environment, record:

- Environment identifier.
- Windows edition, version and build.
- CPU architecture and available memory.
- Application version and artifact SHA-256.
- Account type and relevant permissions.
- Test date.
- Scenario IDs and outcomes.
- Relevant sanitized evidence.
- Known limitations and unresolved defects.

Do not claim support for untested Windows configurations.

## 5. Release-blocking conditions

The following require resolution or an explicitly approved release disposition
before the affected production claim can be made:

- Unauthorized consequential operations can execute.
- Required eligibility, decision, authorization or verification boundaries
  can be bypassed.
- A serious reproducible defect risks data loss or system integrity.
- Release artifact integrity cannot be established.
- Required startup or shutdown behavior fails without an understood disposition.
- A claimed capability has no supporting implementation or validation evidence.

A failed test must not be reclassified as passed merely to complete the matrix.

## 6. Beta completion decision

A beta acceptance decision should summarize:

1. Total scenarios run, passed, failed, blocked and not applicable.
2. Windows environments actually tested.
3. Open defects and their severity.
4. Security and remediation-boundary test results.
5. Artifact integrity result.
6. Known limitations and accepted risks.
7. Final decision and responsible reviewer.

Beta acceptance is not proof of universal compatibility or publisher authenticity.
Digital-signature status must be reported separately from hash verification.
