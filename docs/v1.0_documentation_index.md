# Windows Technician V1.0 — Documentation Index

## Purpose

This index identifies the primary documentation for Windows Technician V1.0.
Documentation describes intended usage and established contracts; actual
application behavior must remain consistent with verified implementation.

## Audience and reading order

### End users
Start with [the End-User Guide](user_guide.md), then consult the
[Troubleshooting Guide](troubleshooting_guide.md) when problems occur.

### Technicians
Read the [Technician Operations Guide](technician_guide.md) for diagnostic
case handling, recommendations, authorization, execution, verification,
recovery and operational history.

### Developers
Read the [Developer Guide](developer_guide.md) before changing implementation
or tests. Consult the architecture document before modifying canonical models
or integration boundaries.

### Beta testers
Use the [Beta Testing Guide](beta_testing_guide.md) to plan scenarios and
report defects. Use the [V1.0 Beta Acceptance Matrix](v1.0_beta_acceptance_matrix.md)
to record results and identify release blockers.

## Architecture and release contracts

- [V1.0 Architecture](v1.0_architecture.md): architecture and system boundaries.
- [Packaging and Release Contract](v1.0_packaging_release_contract.md):
  executable build and artifact integrity expectations.
- [Phase 14 Performance and Scale](phase14_performance_scale.md):
  performance and scale considerations.

The architecture and release-contract documents are not replaced by this index.

## Canonical operation safety

The documented operation pipeline is:

Evidence -> Reasoning -> Recommendation -> Eligibility -> Decision ->
Authorization -> Execution -> Verification -> Recovery and History

User-interface, remote and fleet integrations must preserve the applicable
authorization and execution boundaries.

## Documentation authority

When documentation conflicts with implementation, tests or a release contract,
record the discrepancy and resolve it. Do not silently assume that a documented
capability exists merely because it appears in a guide.

## Release limitations

A SHA-256 match establishes integrity against the expected manifest. It does
not establish publisher identity. Digital-signature verification must be
reported separately.
