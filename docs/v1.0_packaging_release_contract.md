# Windows Technician V1.0 — Packaging and Release Contract

## Purpose

Define a controlled route from the Python application to a verifiable Windows
release artifact. This contract extends the existing `packaging` architecture;
it does not replace runtime configuration, application bootstrap, lifecycle,
security, recovery, or operational logging.

## Build inputs

- `main.py` is the application entry point.
- The source root is explicit and independent of the caller's current directory.
- Production dependencies and build-tool dependencies must be managed separately.
- Resource inclusion must be deliberate and tested against the packaged application.
- Build output must be isolated from source files.

## Build behavior

The release pipeline must:

1. Validate the source root and application entry point.
2. construct a reproducible, explicit PyInstaller command.
3. stop when the build tool is missing or the build fails.
4. verify that the expected executable exists after a successful build.
5. record artifact size and SHA-256 in a release manifest.
6. never report a successful release merely because a build command returned zero.

## Integrity and trust

A SHA-256 manifest detects accidental changes when the expected hash is trusted.
It does **not** authenticate the publisher or prove that an executable is safe.
Production distribution must separately establish code signing, signature
verification, trusted update metadata, and a secure release channel.

Secrets, credentials, and machine-specific user data must not be embedded in
the executable or release manifest.

## Runtime and data boundaries

The packaged application must not assume that the source checkout is writable
or present. Runtime configuration, logs, state, and user data must use the
existing runtime-path architecture and appropriate per-user or system locations.

Upgrades must preserve user data. Repair and uninstall must distinguish
application-owned files from user data. Destructive cleanup requires explicit,
informed policy and must not be inferred from an installer default.

## Validation gates

A passing unit-test suite is necessary but insufficient. Release validation
must include:

- executable build and artifact inspection;
- launch from outside the source directory;
- launch on a clean Windows environment without a Python development setup;
- configuration, logging, and resource resolution;
- installation, upgrade, repair, rollback, and uninstall behavior;
- signature and update-integrity validation;
- failure and recovery scenarios.

## Scope

This document establishes the Phase 16.1 release contract and the initial
build-pipeline boundary. Installer implementation, migration, update delivery,
code signing, and packaged-machine validation remain separate implementation
and validation tasks.
